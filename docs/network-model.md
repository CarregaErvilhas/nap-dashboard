# Network model (`chargers.json`)

The producer-side description of the file this repo publishes at `https://nap.ocarroeletrico.com/ohmigo/chargers.json`. Rules for changing it are in [AGENTS.md](../AGENTS.md).

## Role

`scripts/ohmigo_dataset.py` builds `data/ohmigo_chargers.json`, **the network model**: the one place that decides what is true about each charger. Two readers: the ohmigo MCP server (EV charging cost answers for ChatGPT/Claude) and this repo's site, whose `build_dashboard.py` takes each socket's power, operator fees, regime and NAP-only issues from it (`site/data/points.json` `kw`/`kw_src`/`nap_kw`/`fees`/`regime`/`nap`/`nap_fees`/`issues`, and each site's `kw` and `dcv` in `sites.json`). Before, the site computed its own from the same CSVs and the two drifted (fees cut to the first €/min tier, kW rounded to the unit, the short-`UID_TOMADA` matches only ohmigo had, OSM's power only ohmigo applied). `scripts/model_parity.py` runs after the build in `refresh.yml` and fails the refresh if `site/data` disagrees with the model of the same run.

The Rede statistics stay on what the NAP declares (`max_power_w`, `pw_class`, `data/nap_opc_points.csv`): they describe the NAP's publication. The OPC tariffs come from `scripts/opc_tariffs.py`, the same join `mobie_join.py` uses for `data/nap_opc_points.csv`, so the stats and the model agree on which socket has which fee.

## Contents

Contents: sites, points, power, the connector's declared tensão (`v`, V) and max current (`a`, A), the grid voltage level (`level`: BTN/BTE/MT, which picks the TAR; **always `null`**, because neither MOBI.Data nor the NAP publishes it) and the **raw** MOBI.E OPC tariffs per socket (every €/min tier and the `AD_HOC_PAYMENT` plan, which `data/nap_opc_points.csv` collapses to one value), whether the cable is attached (`cable`, from `connectorFormat`), the NAP's site `name`, opening `hours` (converted by `nap_etl.py` from DATEX II `operatingHours` to OSM `opening_hours` syntax: `24/7`, `Mo-Su 09:00-21:00`), `locationDescription` ("Parque Coberto - Piso -1") and the operator's `phone`,

plus a per-site `osm` block (name, brand, operator, opening hours, location, access, parking fee, maxstay, level, covered, indoor, phone, email, manufacturer, model, capacity, `payment` = the `payment:*`/`authentication:*` methods tagged yes, and `cards` = true/false when OSM says whether a bank card works at the charger) and a per-point `osm` with the kW/V/A of the matching OSM `socket:*` (same plug type, nearest power), **only where it differs from the NAP** — read off the charger's plate by the community, it is usually more right than the NAP's declaration (DC placeholders 750/600 V, impossible powers), so the model applies it: `kw`/`v`/`a`/`cable` are OSM's and the NAP's value goes to `napKw`/`napV`/`napA`/`napCable`, present only when replaced (`null` = the NAP declared none). An OSM number has to be plausible first (`osm_tags.sane_osm`: at most 1000 kW / 1500 V / 1500 A, and within ×20 kW or ×10 V/A of a plausible NAP value), or it is dropped. ohmigo made this call itself until the model did; it now reads the result.

Per point, `issues` lists what the NAP-only rules of `nap_static_checks.py` found on it (`tensao_placeholder`, `trifasico_sem_3p`, `tensao_em_falta`, `tensao_impossivel`, errors.md item 8). Each point also has `evse`, the NAP `point_external_id` exactly as published (`PT*EDP*E*LSB*90050*01`), the id on the socket's sticker: the point `id` is only unique within its site, so this is what a link to one socket uses (VoltFrame). Not guaranteed unique (a few operators publish the same id on two sites) and never a join key: the NAP↔MOBI.E join rule in [AGENTS.md](../AGENTS.md#data-gotchas-verified) stands.

Nothing from the PCVE tracker goes into the model: it is a third party's data with no reuse licence, and the model is public.

Where OSM agrees with the NAP, the point lists those fields in `osmSame` (`["a", "v"]`), so ohmigo can tell a value confirmed on the charger from one only the operator declared (a DC socket's current decides the power a 400 V car gets).

## Joining OSM to the NAP

All joined from the Overpass dump in `data/umap_cache/todos.json` by `ref` = NAP `external_id` (any code form, so Continente's `0001PL0002` joins too; ≤1 km from the NAP point, or farther in the right concelho, below). A `MOBI-` prefix on the OSM `ref` is dropped only when the ref as written is not a NAP code (`osm_tags.nap_code`): some NAP sites really are `MOBI-XXX-00000`, some next to a `XXX-00000`, and stripping it always left them unmatched. An element whose `ref` is no NAP code (missing, a typo like `MLG-00022`, a bay number like `1A`) joins by its `ref:EU:EVSE` instead: each socket id (`PT*EDP*E*MGL*00022*1`, `evse_key`) names its NAP point and so its site (`osm_tags.evse_sites`; an id the NAP gives two sites is dropped). The `ref` wins when both are there.

Elements mapped as `disused:`/`construction:` `amenity=charging_station` or `man_made=charge_point` (`osm_tags.lifecycle`) are the site's element for the link only, after any in-service one: their tags are not today's charger. When a site has only such elements, the `osm` block says so in `lifecycle` (`disused` | `construction`, from the element linked) and `sites.json` in `olc`. OSM decides the life cycle of a site the NAP still publishes: Procurar counts it as disused / under construction ("Estado do posto" filter, hidden by default) **unless the operator reports a socket `available` or `charging` now** (live status, or the week's when live is off): then it is in service and the detail says OSM is out of date. The Rede statistics are unchanged: they describe the NAP's publication.

It's what lets ohmigo find "o posto do Lidl de Coimbra": OSM's `brand`/`operator` are often the owner, not the CPO (Lidl owns its chargers, Galp operates them: the NAP says Galp, OSM says Lidl). Additive and optional, so no `SCHEMA` bump; without the dump (osm_umap.py not run) sites just lack `osm`. ODbL: see `THIRD-PARTY-NOTICES.md`.

## The `osm` block

The `osm` block also has `hardware`: every charger make + model mapped at the site, most common first (`["ABB Terra HP CP4", "Alpitronic HYC_400"]`; `manufacturer`/`model` are only the commonest). The site shows the same list (`hw` in `sites.json`, "Carregadores: …" in the detail) and its search finds a site by it. Both come from `scripts/osm_tags.py`, so the site and ohmigo never disagree about a charger.

The `osm` block also has `element`, the OSM element the site is matched to (`"node/123"`, `"way/456"`: an element with only this `ref` before a shared `"A;B;C"`, then the whole site's `amenity=charging_station` before a `man_made=charge_point`, then the nearest); `sites.json` carries it as `osm_ref` (the planned sites already had one), and Procurar's "Ver no OSM" opens that element, falling back to a marker at the coordinates. An element > 1 km from the NAP point counts only when its point falls in the concelho of the site's code (`far_ok`, from `concelho_check.py`'s `conc_code`): otherwise it is a wrong `ref` on OSM and is left out.

## Position

**The site's position is OSM's**: `lat`/`lon` are those of the element linked (unless it is shared, "A;B;C"), and the NAP's go to `napLat`/`napLon` when different (OSM, mapped on site, is always more right than the NAP, which puts some sites in another concelho). `region`, `places` and `nearby` follow the new position. Procurar takes the position from the model (`model_parity.py` checks it) and warns in the detail past `OSM_DIVERGE_KM` (300 m).

## Shared fields (`osm` block and `sites.json`)

Also from `osm_tags.py`, in both the `osm` block and `sites.json`:

- `sharedKw` (`shared`): the total a charger declares (`charging_station:output`/`charge_point:output`) when it is below its sockets charging together. DC plugs of one multi-standard charger (CCS + CHAdeMO) don't add up, only the largest DC type × its count plus the AC sockets, so a 50 kW triple charger with a 50 kW CCS is not "shared".
- `oldRefs` + `oldOperator` (`old`, `oldop`): OSM `old_ref`/`old_operator`, the sticker of a charger that changed operator. An old code that is another site's code now is dropped. Searchable on the site and in ohmigo.
- `wheelchair` (`wc`): OSM `wheelchair` yes/limited/no; the site and ohmigo also read the NAP's DATEX II `accessibility` (`nap_etl.py` writes it to `nap_static_sites.csv`; `wheelChairAccessible`/`disabilityAccessible`/ `barrierFreeAccessible` = yes). The "Acessível em cadeira de rodas" filter keeps yes and limited; very few sites say anything, and the help text says that missing information is not "inaccessible".
- `fixme`: the community's open questions on OSM, shown on the site as "Por confirmar no OpenStreetMap"; ohmigo keeps up to 3, cut at 160 characters, and tells the assistant to present them as things to check on site, never as facts.

## Per-element `evse`

- `evse` in the `osm` block (dataset build only, never written; not the point's `evse` above): OSM `ref:EU:EVSE` per element, matched to the NAP `point_external_id` (`evse_key`), so a socket's OSM kW/V/A come from the element that is that socket; the plug + nearest power match over the whole site stays the fallback.

## Places

Also per site, `places`: the shopping centres, hospitals, universities, airports, stadiums, supermarkets, car parks and hotels (named, from OSM) whose outline holds the site or lies a few metres from it, `{name, type, osm, m}` (`m` = metres to the edge, 0 = inside; up to 3, inside first). OSM doesn't say which place a charger is at, so `scripts/osm_places.py` works it out (point in polygon, stdlib only) from `data/umap_cache/places.json`, which it builds with `osmium` (pyosmium) from Geofabrik's Portugal extract: `refresh.yml` downloads `portugal-latest.osm.pbf` (~400 MB) and runs `python scripts/osm_places.py <pbf>` (~10 s) with `continue-on-error` before the dataset; without the cache sites just lack `places`.

Overpass was tried first and timed out even on half-degree tiles. The radius outside the outline depends on the type (a hotel or car park only counts right beside it), and a place whose name repeats one already kept is dropped (two OSM objects for the same mall, "Centro Comercial Colombo - Estacionamento Piso -1"). It's what lets ohmigo find "os postos do Mar Shopping", which no charger is named.

## Publishing and guards

No status and no CEME prices: ohmigo reads status live from the NAP feed and gets energy prices from ceme-v2. `refresh.yml` builds it before the site (the site reads it) and uploads it with the site's data, only after the pipeline guard, the parity check and `validate_site.py` pass, in the `network` Actions artifact (see [workflows.md](workflows.md); not committed; not a release, because the repo's releases are immutable and an asset can't be replaced); `pages.yml` publishes the newest one at `https://nap.ocarroeletrico.com/ohmigo/chargers.json`. It exits non-zero (and the refresh fails) below 5 000 sites or 10 000 tariffed points. `SCHEMA` in the script bumps on incompatible format changes.

## Charger models

Also per site, `models`: the charger models of `scripts/charger_models.py`, from the catalogue its maintainer keeps in a Google Doc ("Modelos de Carregadores usados em Portugal": per model and version, total kW, max V, cable A, and the kW **each car** gets at 400 V and 800 V with 1, 2, 3… cars plugged in). It is the same file `hardware_checks.py` reads (`fetch_charger_models.sh` -> `data/charger_models.txt`): public and free to use, credited with its link (`charger_models.SOURCE_URL`) wherever its figures are shown; only its numbers are used, never its photos or operator logos (they are not the author's).

`charger_models.load` refuses a catalogue of under 50 models, so a document that changed format can't empty every site's `models`. A version starts at a `§.Marca.Modelo` line or, for the brands without one, at the name line right before its power line, under the latest brand header with flags ("Wallbox 🇪🇦").

The join to a site is the OSM `hardware` (`charger_models.match`: same name once normalised, or OSM more specific, "iFC160-350A"; a part of a set, "blueberry PLUS", matches every set it is in; `LABEL_ALIAS` for names OSM writes differently). Of the model's versions, only those whose amps and kW fit the site's sockets stay (`variants`, cars = `[n, kW at 400 V, kW at 800 V]`); none better than the others keeps them all. Each point gets `model` (index into `models`) when it can be told: the only DC model, else the one whose one-car kW is nearest; an AC socket, the only model with AC; a DC model no DC socket can be (they all declare more than it gives: OSM has an old charger) leaves the site. Top-level `modelsSource` carries the author and title for the credit. `python scripts/charger_models.py --labels data/ohmigo_chargers.json` lists the OSM names that match nothing. The site shows them in Procurar's detail (`mdl` in `sites.json`, `mi` per point).

## Photos

And `photos` (per site) and `models[].photo`: thumbnails from `scripts/charger_photos.py`. A site's own photos are, first, its main photo on olh'o'posto (`olhaoposto.ocarroeletrico.com/api/v1/main-photos`, moderated, CC BY-SA 4.0; ref `olhaoposto:<NAP site id>`, re-downloaded when its `publishedAt` changes, since the static URL stays the same; kept as they were when that API is down), then every other photo olh'o'posto published of the site and its sockets (`/api/v1/photos.json`, `origin` `olhaoposto` except the station's main and the rating plates, `kind` `plate`; ref `olhaoposto-photo:<photo id>` with `site` = the NAP site id, the thumbnail from `pictures.*` or olh'o'posto's Panoramax, oldest first; also kept when that file is down), then up to 3 OSM references (`osm_tags.photo_refs`: `panoramax=`, `mapillary=`, `wikimedia_commons=`, `image=` pointing at one of them; MapComplete's charging-station theme saves photos on Panoramax). A `panoramax=` UUID is looked up in the federated search (`api.panoramax.xyz`) and, when it is not there, in olh'o'posto's own Panoramax (`panoramax.ocarroeletrico.com`, outside the federation for now), whose author comes from the `OlhaOPosto|author=` tag, not the producer (always the service account); when that UUID is also one of the site's olh'o'posto photos, `ohmigo_dataset.py` keeps one. All of the olh'o'posto photos are shown, the OSM ones only up to 3.

A model's photo is a Commons file chosen by hand per catalogue key in `assets/charger_model_photos.json` (a photo of the same model, not of the site: everyone who shows it says so). The script downloads a 500 px thumbnail of each to `data/photos/<id>.jpg` with author, licence and source page in `data/photos.json` (cached between runs; Mapillary is a link only, its API needs a key). The thumbnails travel in the `network` artifact with the JSON, and `pages.yml` publishes them under `/photos/` (JPEG only, `<16 hex>.jpg`, < 400 kB): the site shows them from its own domain, so the CSP and the privacy page need no third party. Procurar links sites without a photo to olh'o'posto's upload page with the site picked (`/enviar?posto=`), so a driver can add one.

## olh'o'posto links

`sites.json` `oop` is the NAP site id (`EZC-AMD-00051`): Procurar links every site to its olh'o'posto page, and an olh'o'posto photo to its place on the Panoramax map (`map`). `?posto=` (NAP code or site id) opens that site's detail; olh'o'posto links here with it. A code the NAP does not have yet opens the site under construction that carries it in `codes`, and its state joins the "Estado do posto" filter so the list shows it. A site under construction with no photo links to olh'o'posto's upload page (`/enviar?posto=OSM-w123`), never to its static links (there are none until it is in the NAP). A code that matches nothing says so (`#postoMiss`), and says the site joined the NAP in the last 24 h when `changes.json` `sites_added` lists it.

## `planned`

Top-level `planned`, beside `sites` (additive, no `SCHEMA` bump): the sites OSM says are under construction or planned and the NAP does not have yet (`osm_planned.py`), `{id, osm: {element}, lifecycle, codes, name, operator, city, region, lat, lon, npts, kw, connectors}`, plus `nap`/`napM` when a NAP site is within 30 m. `id` is the OSM element (`OSM-w123`, `OSM-n123`), `lifecycle` is `construction` | `planned`, `codes` the NAP codes written on it ([pipeline.md](pipeline.md#planned-sites-osm_plannedpy)), `connectors` in the model's names (`CCS`, `T2`, `CHADEMO`, `MCS`), `kw` the largest socket output mapped or `null`. olh'o'posto imports the `construction` ones so people can send photos before the charger opens, and merges one into the NAP site when its code or OSM element shows up in `sites`. A site leaves `planned` as soon as the NAP has one of its codes. When a NAP site lies within 30 m, the entry stays with `nap` (that site's id) and `napM` (metres): it may be the same charger with a stale OSM tag, or a new one beside it, and olh'o'posto's moderators decide. The key is left out when `osm_planned.py` did not run (no OSM dump): a reader keeps what it had, while `[]` means there are none.

## Extra fields for drivers

More per site and per socket for drivers, all additive (no `SCHEMA` bump):
- `unit` (per DC point): which charger of the site the socket is on, from the OSM posts (`man_made=charge_point` with the `ref:EU:EVSE` of several sockets, `osm_tags` `units`), numbered in socket order, only when two or more DC sockets of the site share it (an AC post's sockets have their own circuits). With the live status, Procurar's detail says "a partilhar com …: até ~X kW cada" (the model's two-car figure) and which charger to pick when another is busy; ohmigo's `lookup_charger` returns `chargers` and `pickCharger`. `points.json` carries it as `u`.
- `underground` (`'osm'` | `'nap'`): an underground car park, from OSM (`location=underground`, or `level`/`layer` below zero, `osm_tags.underground`) or the NAP's `locationDescription` ("Parque Coberto - Piso -1"): often no mobile signal, so open the app before driving in. `sites.json` `ug`.
- `osm.checkDate`: the latest `check_date`/`survey:date` on OSM, when someone checked the charger on site. `sites.json` `chk`.
- `nearby`: cafés, restaurants, fast food, toilets, shops and fuel stations within 150 m, per type `{type, n, m, name}` (`osm_places.nearby_for`, from `data/umap_cache/amenities.json`, which `osm_places.py <pbf>` writes from the same Geofabrik extract as `places`). `sites.json` `nb`.
- `history`: the site in the AmpereArchive, `archive_stats.site_stats` (same spans as the per-operator stats), written by `archive_history.py` to `data/site_history.json`: `down`, the % of the observed time its sockets were `outOfOrder`/`inoperative`, and `busy.wd`/`busy.we`, the % of the time they were charging per local hour on weekdays and weekends (`null` for an hour with under 2 days of data); `days` behind it, and nothing under 7 days. Top-level `historySource` has the window. `refresh.yml` computes it on every run and keeps the last good one in `actions/cache`, for a run where the archive fails. `sites.json` carries `hd`/`hn` and `hb`, 48 characters (weekdays then weekends, the tenth of the %, `.` = no data). Procurar shows `hd`/`hn` ("Avarias") but no longer draws `hb`: the usage charts come from the AmpereArchive's per-site files (`uso.js`, [site.md](site.md)). Rede > Operadores has "Que carregadores usa cada operador" (`stats.json` `op_models`): the models joined at each operator's sites, top 20 operators.
